# 两个真实仓库的独立静态评审

评审对象是 CallScope 的多语言扩展及其对 WinWinCode、CodePatchBay 源码的解释能力。目标仓库只作为只读源码数据；本评审没有导入、执行、构建或测试目标，也没有调用其 Beads、code-index 或其他仓库命令。报告属于 CallScope 评估产物，不是两个目标仓库的任务记录。

## 评审状态

已完成多语言协议、两个仓库代表性生产入口、统一编排器、读取器、TypeScript/Rust 前端、配置/版本整合及保存扫描产物的独立复核。已报错误确定性问题均已修正；首轮真实规模暴露的证据放大问题也已修正，根代理已完成两个仓库的新版本扫描、发布和完整导出，保存摘要与见证身份一致。

**可以交付为受限静态调用结构工具，当前没有剩余已确认的 P0/P1 阻断；“全项目架构异常检测”和功能正确性仍未得到本轮证据支持。** 两库均明确保持 `partial`，关键组合入口解析缺口、动态分派及真实架构规则缺失需要保留在结论中。本轮没有浏览器交互验证，不能宣称界面交互已经通过。

本评审者只进行了源码、配置和保存产物的阅读；没有启动服务、运行分析器或浏览器，也没有建立或运行测试。根代理正常使用 CallScope 读取目标源码、查询保存图和启动工具界面，与执行目标程序是不同的操作。其实际使用观察将与本人的源码复核分开记录。

## 独立需求判断

增加 TypeScript 和 Rust 是针对真实仓库覆盖不足的合理修正。仅扫描 Python 而未覆盖主产品语言，无法评价这两个仓库的主要调用结构。但是，解析更多语法仍不等于理解业务完整性；Tree-sitter 提供语法树，不自动提供模块解析、作用域、类型分派、宏展开或构建配置。

本轮可以评价三件事：主要配置范围是否被读取；源码中明确的静态调用能否保留为有位置证据的连接；不受支持的连接是否透明地保持未知。不能把自设的 `required_path` 当作项目原有需求，也不能把“这条已知源码连接应能被工具找出”的能力基准失败转写成项目架构缺陷。

## 审查重点及判定口径

- TypeScript：词法块与函数作用域、参数和赋值遮蔽、类型名和值名、`.js` 源码映射、别名及重导出。接口/对象/回调分派和 JSX 渲染关系无法确定时必须显式保持未知。
- Rust：crate 与模块身份、`use/pub use`、多个同名实现、闭包/局部绑定、trait 方法、`cfg` 与宏。未展开的宏和条件编译不能当成空的确定实现，也不能生成未经依据的实际构建配置。
- 编排：前端只解析统一捕获的文本；文件失败、缺少语法库、未支持扩展名、模块冲突和相关未知不被吞掉。语言、前端版本、语法库与宿主版本进入身份，证据仍来自同一快照。
- 评估：真实源码观察、工具能力基准、项目明示约束和待确认架构疑点分别表述。禁止通过增加人为约束制造“项目缺陷”。

## 可交付范围与已知缺口

**可以交付的是源码证据浏览与受限静态连接核对。** 同文件函数、明确的 ES 模块导入/重导出、部分 Rust crate/module 自由函数调用具有直接价值；不能因此宣称全项目的业务链路已连通。动态 CLI 路由、对象与接口注入、Rust trait、宏、JSX 生命周期和跨语言进程/协议关系，在这两个仓库中都是主要架构组成，并非可以忽略的边角语法。

**WinWinCode 前端组合根的解析缺口必须单列。** 保存结果确认固定语法库无法完整解析 `apps/client/src/application.ts:966` 的 inline import 类型，整文件保留 `parse_error`，基准的嵌套源端点不存在。这是工具能力缺口，不能称为项目代码错误；它影响挂载/组合入口及工作区别名链路的核对，不能用其他文件的解析数量抵消。

**负向结论比正向连接更弱。** 已找到的确定边可以提供局部符号绑定见证；没有找到路径，只有在明确的静态模型、有效端点和相关完整性条件下才成立。目前部分覆盖缺口采取全局保守传播，会使原本局部可判断的规则也显示未知。这是有意降低错误确定性造成的能力限制，不能把“无违规发现”解释为规范已证明。

**输入快照是保存文本集合，不是 Git 提交或文件系统原子快照。** 源文件哈希使证据可追溯，但若工作区在捕获过程中改变，多文件可能来自不同瞬间。当前应在稳定源码范围评估；如以后需要审计级提交归属，应从固定对象树捕获或增加明确的一致性检查，不能仅附上工作区 HEAD 就升级保证。

**Rust 图是源码声明视图。** 未选择 Cargo feature、target 与宏展开结果，`#[cfg(test)]` 内联模块仍可能被索引；没有执行测试不代表图里不存在测试声明。保留未知条件是正确行为，但节点数量不能称为生产构建覆盖，`resolved` 也不证明可见性、类型检查、编译或实际加载成功。

## 对需求和后续范围的独立建议

保留统一捕获、语言前端、确定/未知边分离、版本化证据、显式约束与源码下钻。这条路径能够支持代码理解和局部架构规则核对；没有必要恢复原案的“数字孪生”“异常总分”或百万节点渲染承诺。

下一步优先修复真实组合入口的语法/模块解析缺口，并按实际缺口增加可审阅的静态绑定能力。对对象注入、宏和注册机制，应先明确什么源码证据足以绑定目标，不能为增加确定路径比例按同名函数猜测。前端协议还应长期保留不完整原因与版本纪律，新增语言必须让失败向上游显式传播。

项目架构规则需要独立的意图依据。当前二十条规则适合核对工具能力，不能当作真实架构缺陷检出集合。若要评价 CodePatchBay 的核心依赖方向，或 WinWinCode 的嵌入式内核/禁用 fallback 意图，需要先把源码导入、外部启动边界和项目声明对应起来，再确认纯调用图是否足够表达；不能默认调用链就能判断所有功能通过。

真实结果还暴露了展示优先级问题：CodePatchBay 的 40,388 项发现主要是未知关系、外部回调边界与配置入口未确定可达说明。53 项循环/递归属于结构事实，也不自动是缺陷。若继续使用原案“人只看异常”的定位，需要将规则违规、结构事实、分析能力缺口分别呈现；未知可按调用者或边界归组，未确定可达可作为按需视图。不能把发现总数当作已检出的架构异常数量。

这些基准中包含容易定位的同文件 helper 与短路径，能够确认基础解析和证据流程，但代表不了架构层面的完整链路。**本轮尚未证明系统能发现真实业务架构异常，也没有建立检出率或误报率证据。** 可验收范围应限定为：声明范围内的源码已捕获且失败透明；人工实见连接具有相同快照的边和源码见证；动态边界不被猜成确定边；两库能够完整发布并下钻查询；未知、策略与人工决定不改写原始事实。

无需在本轮增加图数据库集群、LLM 评分、时序统计或性能优化。当前主要限制来自静态语义范围和真实规范缺失，而非存储吞吐。用户禁止测试和目标执行的边界应保持，结论也相应限于可观察的源码结构。
